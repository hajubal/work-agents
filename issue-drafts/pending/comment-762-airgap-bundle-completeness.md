# [코멘트 초안] #762 — 폐쇄망 번들 완결성 후보를 이 이슈로 흡수 (+ 시장 근거는 무너졌다)

> 대상: #762 코멘트 (신규 이슈 아님)
> 기획 사이클: 2026-08-pilot · 2-plan.md 후보 #5 [M] · 승인: 4-decision.md (2026-08-13)

## 결정

2026-08-pilot 기획 사이클의 후보 5 "폐쇄망 번들 완결성 — 모델 수급 구멍 제거 + 설치 전 자가검증"이 승인됐고, **신규 이슈를 만들지 않고 #762로 접는다.** 이 티켓에 실측 근거·제안 3안·수용 기준이 이미 다 적혀 있고 담당자도 지정돼 있으니, 기획 후보로 다시 세우면 같은 일을 두 번 발주하는 것이다. plan 자신도 "#762와 거의 동일 — 중복 발주 위험 최대"라고 적었다.

**#762의 수용 기준은 손대지 않는다.** 아래는 이 사이클이 그 위에 얹는 것만이다.

## 이 사이클이 더하는 것

### 1. 시장 근거가 무너졌다 — 이 티켓의 성격 판정

기획 초안은 이 작업을 "증명 가능한 에어갭 = 유일하게 비어 있는 경쟁 칸"이라는 시장 근거 위에 세웠다. 그 근거가 3-critique.md R2에서 정면 반박됐다.

- 조사가 "고객 전용 포털이라 접근 불가"로 처리한 Lakera self-hosted 문서의 **공개판이 존재한다** — `platform.lakera.ai/docs/self-hosted-setup`·`/docs/deploy-to-k8s`. 리소스 요구·사이징·레이턴시 벤치마크·Helm 설치 절차·GPU 구성·오토스케일링·보안 하드닝·컨테이너 버전 핀까지 다룬다. 조사에서 이 URL은 시도조차 되지 않았다 (3-critique.md 출처 표본 검증 5건 중 유일한 **불일치**)
- 4-decision.md는 로드맵 델타 R3("에어갭 실증을 1급 차별점으로 승격")을 승인하면서도 이 반박을 미해결로 병기했고, "Lakera self-hosted 공개 문서 재조사"를 다음 사이클 조사 항목으로 넘겼다

**따라서 #762는 마케팅 차별점 개발이 아니라 배포 결함 수정으로 다룬다.** 시장 근거가 사라져도 결함 자체는 남는다는 것이 승인의 실제 이유다. 릴리스 노트·영업 자료에 "경쟁사에 없는 에어갭"으로 쓰지 말 것 — 재조사 결과가 나오기 전까지는 근거가 없다.

참고로 남는 근거는 이 정도다. 경쟁 매트릭스 배포 모델 열에서 에어갭이 `[공식]` 근거로 확인된 행은 0개이고 Bedrock은 명시적 불가다([공식] https://aws.amazon.com/bedrock/guardrails/ · 확인일 2026-08-12, G§Q1). F5는 제품 페이지 문구 수준이다([마케팅] https://www.f5.com/products/ai-guardrails · 확인일 2026-08-12). 국내 벤더 중 에어갭 근거를 문서로 제시한 곳도 0곳이다(D§Q2). 다만 R2가 지적했듯 이 "0곳"은 **부재가 아니라 확인 실패**일 수 있다.

### 2. 저장소 재확인 (확인일 2026-08-12, 기준 커밋 `68338338`)

#762가 지목한 결함이 오늘도 그대로다.

- 번들 생성기 `sgt-owasp/scripts/package_models_inference.py`가 `onnx/`* 를 "불필요 포맷"으로 제외한다(L105)
- `triton_repo` 문자열은 저장소에서 **0건**인데 `docs/offline-package-guide.md`는 `triton_repo/toxic_classifier`가 **이미 있다고 전제**하고 복사만 시킨다
- toxic의 `model_type` 기본값이 `safe_classification`(Triton ONNX 경로)이라 **아무 결정을 안 하면 이 경로로 간다**
- `docs/offline-package-guide.md`·`helm/check-models.sh` 존재도 확인

### 3. 추가 요구 — 반입 후 자가검증을 표준 절차에 넣는다

#762 본문에 없는 몫은 이것 하나다. 번들을 반입한 뒤 **설치 전에** 번들 자체가 완결됐는지 검사하는 단계를 설치 절차에 포함한다.

- 기존 `helm/check-models.sh`(설치 전 모델 존재 확인)와 `MODEL_VERSIONS.json`(sha256 원장)을 **잇는 형태**로 붙인다. 신규 도구를 만들 자리가 아니다
- 운영자 조작 경로는 admin UI도 sgtctl도 아니고 설치 절차의 셸 단계다 — 풀·최소 구성과 무관하다
- 실패 시나리오(한국증권금융 toxic 첫 배포): 가이드대로 번들을 만들어 반입 → `triton_repo/toxic_classifier/1/model.onnx`(1.74GB)가 없다 → Triton이 toxic을 0개 로드 → owasp `/health/readiness`가 503으로 잡아낸다(#760 이후 fail-loud) → **현장에서 배포가 뜨지 않는다.** 검사 단계가 있으면 이 실패가 설치 전으로 당겨진다

### 4. 인접 티켓 판정과 규모

- **#519 → 분리**. 현대차증권 패키징은 docker compose 기반 납품 건이고 **PII+JB만 쓰므로 toxic ONNX 경로에 걸리지 않는다**. 다만 2인 중 1명의 일정을 이미 점유하고 있다는 사실은 착수 시기 판단에 들어가야 한다
- **#801 → 분리**. baked 이미지 버전 동기화 사각지대(가드 밖 4곳)로 번들 모델 수급과는 축이 다르다. 티켓 스스로 "우선순위 낮음, 단 첫 baked 고객 전에는 정리"라고 판단하고 있다
- **[M]** — 2-plan.md 표기 그대로. 읽는 기준은 4-decision.md에서 승인된 2-plan.md 머리의 정의표다(개발 2인 기준 달력 기간, 설정 전파 양쪽 + DB 마이그레이션 1세트 + 문서 + 재측정 포함, 고객 유지보수 창·외부 시험기관 일정 제외. [M] = 2~4주)
- 내역: 코드(패키저 + 검사 스크립트) + 문서(오프라인 가이드·helm README) + 릴리스 재빌드/재검증 1회. **DB 마이그레이션 없음, 설정 전파 없음**(설치 시점 산출물). 다만 모델 재배포 전 **라이선스 확인**(Gemma Terms 등 외부 모델 조항)이 코드 밖 선행 작업으로 붙는다
- 담당 리스크: 개발 후보가 아니라 릴리스 엔지니어링 작업이라 2인 중 누구 몫인지가 별도 결정이다
