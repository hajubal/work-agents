# feat(admin): 탐지 민감도 프리셋(관대/기본/엄격)

> 기획 사이클: 2026-08-12-pilot · 2-plan.md 후보 #3 · 승인: 4-decision.md (2026-08-13)
> 변경 지점이 admin·sgtctl·owasp에 걸친다. Requirements의 `[admin]`/`[ctl]`/`[owasp]` 태그가 2인 분담선이다 — `[owasp]`만 owasp 담당, 나머지는 다른 1인 몫이다.

## Problem

민감도 축이 세 서비스에 서로 다른 형상으로 흩어져 있다. PII는 `pii_entity_thresholds.json`, toxic은 `toxic_config.json`, JB만 **모델 설정 파일 안**이다(#826 본문 표).

그래서 오탐이 터졌을 때 JB 민감도 하나를 낮추려면 `model_path`를 포함한 모델 설정 전체를 오버레이해야 하고, 그 순간 그 사이트의 모델 경로가 고정돼 이후 모델 업그레이드가 조용히 덮인다(#826). 현장이 라벨별로 조정하는 대신 `_default`를 1.1로 올려 통째로 끈 것도(#816 §1) 이 구조와 무관하지 않다.

## Goals

- 프리셋 하나를 고르면 PII·toxic(그리고 #826 이후 JB) 값이 한 번의 조작으로 함께 바뀐다
- 프리셋과 개별 threshold가 동시에 지정됐을 때 어느 쪽이 이기는지가 문서와 코드에서 같고, 화면·CLI가 그 결과값을 보여준다
- 각 프리셋에서 사실상 비활성이 되는 라벨 목록이 **적용 전에** 표시된다
- 같은 프리셋 이름으로 풀·최소 두 구성에서 동일한 탐지 결과가 나온다

## Non-Goals

- **#826** (JB 민감도를 모델 설정에서 분리) — 선행 의존이다. 모델 경로 오버레이가 업그레이드를 덮는 결함은 이 이슈 없이도 독립 가치가 있고, JB 축을 프리셋에 넣으려면 #826이 먼저 닫혀야 한다. **#826 전까지 JB는 이 이슈 범위 밖이다**
- **#720** (로컬 폴백 ↔ admin 시드 임계값 불일치) — 선행 의존이다. 정합이 안 된 상태에서 프리셋을 얹으면 원장이 셋이 된다
- **#816** — 1회성 A/B 측정 리포트다. 관계는 중복이 아니라 입력이며, 프리셋 각 단계의 값을 정할 근거표가 #816 §1이다
- `compliance_modes.json`(kr_pipa / us_hipaa / eu_gdpr / strict)·`unified_policy.json` 확장 — 이들은 **주소 마스킹 정책**(보존 레벨·마스킹 문자) 전용이지 탐지 민감도 프리셋이 아니다. 네이밍·화면 배치에서 충돌하지 않게 하는 것이 설계 제약이다

## Requirements

- [ ] [owasp] 프리셋 3~4단계 각각의 값 조합(toxic 카테고리별 threshold, PII per-entity threshold)을 정의한다. 값의 근거표는 #816 §1이다
- [ ] [owasp] 프리셋과 개별 threshold의 **우선순위 해석을 코드 한 곳**에 둔다. 이중 원장을 만들지 않는다
- [ ] [admin] `templates/detection/config.html`에 프리셋 선택을 추가한다. 현재 이 화면에는 PII 엔티티별 슬라이더, toxic 카테고리별 슬라이더, "설정값 되돌리기"만 있고 JB 관련 항목은 없다(저장소 검색 0건)
- [ ] [ctl] sgtctl 설정 화면에 프리셋 항목을 추가해 한 번의 편집이 `toxic_config.json`과 `pii_entity_thresholds.json`을 함께 쓰도록 한다. 금칙어가 `words`+`enabled` 두 키를 함께 쓰는 기존 패턴과 같은 방식이며, 반영은 롤링 재기동이다
- [ ] 프리셋 이름과 값은 풀·최소가 **같은 정의**를 쓴다. 값이 갈리면 #720의 재현이다
- [ ] [admin][ctl] 각 프리셋에서 사실상 비활성이 되는 라벨 목록을 적용 전에 보여준다. 지금은 운영자가 각 파일을 따로 열어 `1.1` 같은 범위 밖 sentinel을 손으로 적어야 하고(sgtctl은 클램프하지 않는다고 README에 명시), 무엇이 꺼졌는지는 아무 화면에도 뜨지 않는다
- [ ] [owasp] 프리셋 단계마다 FPR/recall 재측정 1회씩(단계 수 × 1회)
- [ ] [docs] README 3곳 갱신
- [ ] 프리셋 기본값을 `init_script.sql` 시드로 넣는 경우에만: [admin] 수동 DB 마이그레이션 1세트(migration 스크립트 + 문서 + 기동 자가검증)
- [ ] 외부 의존 없음 — 신규 모델·데이터셋 반입이 없으므로 오프라인 패키징 변경은 없다

## 경쟁·시장 근거

- Lakera가 정책별 L1(Lenient, "very few false positives") ~ L4(Paranoid, "higher false positives but very few false negatives") 4단계로 **민감도를 제품 기능으로 승격**했다. 확인된 오탐 대응 수단 중 가장 구체적이다. [공식] https://docs.lakera.ai/docs/policies · 확인일 2026-08-12 (G§Q5-c). 3-critique.md 출처 표본 검증 1번에서 **일치** 판정
- 명시적 민감도 등급을 가진 곳은 확인된 6곳 중 Lakera 1곳이다. Bedrock의 카테고리별 강도 등급은 이번 조사에서 원문 미확인, 나머지 4곳은 미확인이다 (G§Q5-c)
- 업계가 도메인 오탐에 쓰는 실수단은 커스텀 정규식(a) + 신뢰도 임계값(c) + 조합형 파이프라인(d)이고, 셋 다 로컬 설정 파일·정책으로 동작해 폐쇄망에서도 성립한다. [공식] https://docs.nvidia.com/nemo/guardrails/latest/about/overview.html · 확인일 2026-08-12 (G§Q5-a/c/d)
- 고객 데이터 파인튜닝을 공식화한 벤더는 0곳이다 — "없다"가 아니라 "확인 못 함"이다 (G§Q5-b)

## Open Questions (미해결 사항)

승인은 됐지만 3-critique.md의 반박은 해소되지 않았다. 아래는 4-decision.md에 ⚠️로 병기된 반박이다.

- **critique R1**(4-decision.md 후보 3): 후보 1과 동일한 반박 — 실측된 실패 모드는 "노브가 없어서"가 아니라 **"노브를 끝까지 당겨도 아무도 손실을 못 보는 것"**. 미탐 회귀 게이트가 리스크 각주로만 남아 있음
- **critique R1의 근거**(4-decision.md 후보 1에 적힌 전문): 대전제("현장엔 조정할 사람이 없다")가 유일한 현장 실측 #816과 정면 충돌. 현대차증권은 이미 threshold를 직접 꺼서(ORGANIZATION·LOCATION·IP·차량번호 = 1.1) 과탐 33%→1%를 얻은 대신 **실제 PII의 62.7%를 미탐**, 그중 1,262건은 "누구도 끄기로 결정한 적 없는" 손실. 후보 1은 **같은 방향 노브를 하나 더 주는** 기능이다. → "고객 편집권 확대"가 아니라 **"억제 상한 + 미탐 가시화"로 재정의** 전에는 1순위 근거 없음
- 즉 이 이슈는 승인됐으나 **"관대 프리셋을 미탐 상한 없이 제공하면 #816의 실패를 제품 기능으로 굳히는 것"**이라는 반박이 살아 있다. 프리셋 설계 시 미탐 회귀 게이트와 억제 상한을 리스크 각주가 아니라 요구사항으로 올릴지가 미결이다
- 로드맵 델타 R1도 같은 조건부로 승인됐다: 방향의 전반부(모델 분기 배제)는 반박되지 않았으나 후반부("고객 편집권 확대")는 #816 실측과 충돌 → "억제 상한 + 미탐 가시화"로 재정의 후 승인이 critic의 요구
- 4-decision.md 부기: 근거 자체는 검증 통과 — Lakera L1~L4 문구 원문 일치
