## 시장 요약 (조사 2건 종합)

1. **에어갭을 공식 문서로 증명한 제품은 확인 범위에서 0곳.** Lakera만 "컨테이너 인터넷 없이 export/load"까지 확인되고 오프라인 라이선스·모델 패키징은 미확인, F5·SentinelOne은 제품 페이지·보도자료 문구 수준, Cisco는 컨트롤 플레인이 벤더 호스팅, Bedrock은 클라우드 전용(G§Q1). 국내 벤더 중 에어갭 근거를 문서로 제시한 곳도 0곳(D§Q2).
2. **국내에 "폐쇄망 LLM 보안 게이트웨이" 실납품 확정 사례 0건** — 폐쇄망은 sLLM 플랫폼(더존·아이티센·네이버)이 가져가고 그 위의 보안 계층이 비어 있다(D§Q2).
3. **탐지 기능을 MCP tool로 노출하는 제품은 6개 중 0곳** — 경쟁은 전부 "MCP를 보호"(프록시·정적 스캐너) 방향(G§Q3). SGT의 MCP 서버는 아직 차별점이며, **추가 투자 없이 우위 유지 + 다음 사이클 재확인**이 맞다.
4. **한국어 축의 경쟁자는 글로벌이 아니라 국내 3사다.** 글로벌 제품 중 한국어 전용 모델은 0곳, KR 개인정보 내장 엔티티도 0곳(전부 커스텀 regex 위임), Bedrock 금칙어는 한국어 미지원(G§Q4).
5. **도메인 오탐에 대한 업계의 답은 "도메인별 모델"이 아니다.** 고객 데이터 파인튜닝을 공식화한 벤더 0곳(전부 미확인), 실제 수단은 커스텀 정규식(a)+신뢰도 임계값(c)+조합형 파이프라인(d)이며 셋 다 로컬 설정으로 동작해 폐쇄망에서도 성립(G§Q5).
6. **오탐 관리의 최고 수준은 Lakera의 정책별 L1~L4 + Policy Impact Simulator**(과거 트래픽으로 민감도별 flagging rate 비교), 국내에선 이로운 LUBS(과잉 차단 완화)가 같은 문제를 겨냥(G§Q5-c, D§Q5).
7. **조달 관문은 이미 열려 있고 경쟁 3곳이 통과했다** — 세이프엑스·Sphinx AI 디지털서비스몰, LLM Capsule 혁신장터. SGT는 어느 경로에도 미등록(D§Q3).
8. 종합하면 SGT의 방어 가능한 축은 **①실증되는 에어갭 ②한국어 전용 탐지 ③MCP 노출** 3개이고, 뚫려 있는 축은 **④고객이 직접 만지는 오탐 억제 ⑤공공 조달 자격** 2개다.

### 1. 고객 편집형 도메인 예외 사전 (PII/독성 allowlist) [M]

- **문제**: 증권 도메인 용어가 사람 이름·주소·기관명으로 탐지된다(브리프 고객 맥락 1). 현장이 실제로 택한 해법은 "그 값만 빼기"가 아니라 **축 전체 끄기**였다 — 현대차증권 운영값은 `ORGANIZATION`·`LOCATION`·`IP_ADDRESS`·`KR_VEHICLE_NUMBER`를 1.1(사실상 비활성)로, `_default`를 0.5→1.1로 올렸다(#816 §1 원본 JSON). 그 결과 과탐은 33%→1%로 줄었지만 **실제 PII의 62.7%를 미탐**하고, 그중 1,262건은 "누구도 끄기로 결정한 적 없는" 손실이다(#816 1차 결론). 값 단위 예외(#734)는 이미 제품에 있으나 **배포 기본값이 규칙 0개**이고(현대차증권 A/B 문서에서도 "규칙 0개 — A/B 동일"로 실측), 편집 경로가 운영자 손에 없어 현장에서 쓰이지 않았다.
- **무엇**: 고객사 도메인 용어를 탐지 예외로 등록하는 사전(정확 일치 / 정규식 / 엔티티 유형 한정 / 문맥 좌우 토큰). 등록·조회 경로는 풀구성=admin UI, 최소구성=sgtctl 양쪽. 예외 적중은 전부 감사 로그에 남긴다.
  - **풀구성(admin UI)**: 탐지 설정 화면(`templates/detection/config.html` — 현재 PII 엔티티별 threshold 슬라이더 + toxic 카테고리 슬라이더 + `modal/pii-form.html` 마스킹 규칙만 있다)에 **예외 사전 탭 신설** → `sgt_app_config` 키 `pii_value_exceptions`로 저장 → Config Server/Bus 전파. owasp 쪽 수신 핸들러는 이미 있어(`main.py:739` 핸들러 등록) **재기동 없이 반영**된다.
  - **최소구성(sgtctl)**: sgtctl 설정 화면에 예외 사전 항목 추가 → `owasp.detectionConfig.files["pii_value_exceptions.json"]` 편집 → `helm upgrade` + 롤링 재기동(sgtctl Phase 1 계약 그대로). **최소구성 불가 아님 — 다만 반영은 재기동 후다.**
  - 두 경로 모두 **파일 전체 교체**(부분 병합 아님)라는 기존 계약을 따른다.
- **동작 시나리오**: 입력 "현대차증권 리서치센터(대표번호 02-3787-2000)로 자료 요청드립니다" → **현재**: 대표번호가 `KR_PHONE`으로 잡혀 마스킹된다(같은 계열의 실측 사례: 법령 소관부처 전화가 confidence 1.0으로 검출돼 **임계값으로는 뺄 수 없다** — `pii_anonymizer.py` 주석 #729 §2). 앞단 agent가 마스킹된 문장을 받으면 흐름이 끊기므로 현장은 축을 껐다. → **후보 적용 후**: 운영자가 규칙 하나를 등록하고(`{"match":"digits","value":"02-3787-2000","entityTypes":["KR_PHONE"],"action":"allow"}` — 풀=admin 화면, 최소=sgtctl) 그 번호만 마스킹에서 빠진다. 같은 문장의 다른 전화번호·주민번호는 그대로 마스킹되고, 적중은 규칙 id로 감사에 남는다.
- **왜 지금**: 오탐 억제 **전용** 메커니즘은 확인된 6개 벤더 어디에도 문서가 없다 — Lakera의 커스텀 정규식은 "탐지를 추가"하는 방향이고 allowlist·예외 사전은 미확인(G§Q5-a, [https://docs.lakera.ai/docs/content-moderation](https://docs.lakera.ai/docs/content-moderation) ), Bedrock은 엔티티 개별 on/off와 NONE 액션(탐지만·조치 없음)까지가 전부(G§Q5-a, [https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-sensitive-filters.html](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-sensitive-filters.html) ). 국내에선 이로운 LUBS가 같은 문제를 겨냥(D§Q5, [https://www.datanet.co.kr/news/articleView.html?idxno=201426](https://www.datanet.co.kr/news/articleView.html?idxno=201426) ) — **비어 있지만 경쟁자가 이미 조준 중인 칸**이다.
- **경쟁 현황**: 매트릭스 기준 "오탐 억제 전용 기능"을 가진 행 없음. 최근접이 Lakera의 L1~L4 민감도(후보 3)와 Bedrock의 엔티티 on/off. (매트릭스 원본: `[competitor-matrix.md](../../competitor-matrix.md)`)
- **SGT 현재**: PersonNameFilter(한국어 문학 오탐 필터)와 MeCab 사용자 사전 4,745종은 있으나 **둘 다 모델 패키지 내부 — 고객이 편집할 경로가 없다**(inventory: AI 탐지 능력·한국어 특화 요소).
  - **이미 있다(저장소 실측)**: 값 예외 목록 #734(CLOSED) — `sgt-owasp/src/app/config/json/pii_value_exceptions.json`. match 4종(`exact`/`digits`/`prefix`/`email_domain`), `entityTypes` 필수·`*` 금지, 인명 규칙은 `requireAny` 또는 `acknowledgeNameRisk` 없으면 거부, 적용 지점은 마스킹 직전 span 필터(`pii_anonymizer._filter_entities_by_value_exceptions`), 로드 실패 시 **예외 미적용(=그대로 마스킹)** fail-safe. 임직원 명부 변환 스크립트와 적용 전 lint/preview 스크립트도 있다.
  - **이미 있다**: 전파 경로 2종(Cloud Config 키 = 무중단 / helm `detectionConfig` subPath = 롤링 재기동).
  - **없다(저장소 실측)**: 편집 UI·CLI — 문자열 `pii_value_exceptions`가 `sgt-admin/src`·`sgt-ctl/internal`·`helm/` 어디에도 **0건**이다. 풀구성은 서버 설정(`server/config/*.html`, `sgt_app_config` 일반 CRUD)에 JSON 문자열을 손으로 넣는 경로만 존재하고 그 절차의 문서화는 `미확인`. 최소구성은 values 손편집.
  - **없다**: 정규식·엔티티 유형 한정 예외(현재 값 단위 4종뿐), **독성·금칙어 축의 예외**(값 예외는 PII 전용).
  - **감사**: 적중은 owasp 애플리케이션 로그 INFO 한 줄(규칙 id만, 값은 어떤 로그 레벨에도 남기지 않음). admin 탐지 감사 DB(`sgt_owasp_api_event`) 컬럼에는 예외 적중 필드가 없다.
- **완료 판정**: (1) 동일 규칙을 풀구성 admin 화면과 최소구성 sgtctl 양쪽에서 등록했을 때 **같은 탐지 결과**가 나온다. (2) 규칙 등록/수정/삭제가 감사에 남고, 적중 건이 **관리 화면에서 조회 가능**하다(현재는 애플리케이션 로그에만 남음). (3) 인명 예외는 보호장치(`requireAny`/`acknowledgeNameRisk`) 없이 저장되지 않는다 — 화면·CLI 양쪽에서 거부된다. (4) 예외 규칙 N개를 얹은 상태로 법령 clean 코퍼스(#729 112종) FPR과 평가셋 recall을 재측정해 **미탐 증가분이 합의된 상한 이내**임을 보인다.
- **규모 근거 [M]**: 코드(admin 화면 1 + sgtctl 화면 1 + 검증 로직 재사용) + **설정 전파 양쪽 배선**(Config Server 키 / helm values) + 문서(README 2곳·최소구성 가이드) + **재측정 1회**(FPR·recall). - **리스크**: (1) 예외 = 탐지 우회 → 감사 로그·권한 분리 없으면 그 자체가 취약점, (2) 설치형이라 사전 반영 경로가 재기동/설정 전파 문제에 걸린다(최소구성은 Config Server·Bus 없음), (3) 사전이 커지면 오탐은 줄고 미탐이 는다 — 미탐 회귀 게이트 없이는 위험.
- **중복 가능 이슈**: #781(도메인 특화 개선 구조 수립), #875(주소 gazetteer·기관 유한목록).
- **기존 이슈 판정**:
  - **#781 → 흡수**(이 후보를 #781 트리의 하위 티켓으로 접는다). #781 본문 "개선 방향 제안 §2 도메인 프로파일 개념 도입"이 **PII 엔티티 on/off(#464)·값 예외(#734)·게이트 예외(#719)·JB threshold(#767)를 고객사/도메인 단위 프로파일로 묶는 것**을 이미 제안하고 있다 = 이 후보와 같은 축. #781은 In progress·코멘트 32건의 우산 티켓이라 별도 신규 발주는 중복이다.
  - **#875 → 분리**. #875는 **미탐을 줄이는** 소스 레벨 개선(주소 gazetteer 행정동 편입, 금융/카드 브랜드 유한목록)이고 이 후보는 **오탐을 줄이는** 예외 등록으로 방향이 반대다. 다만 둘 다 `ORGANIZATION`·`LOCATION` 라벨을 건드리므로 **재측정 게이트를 공유**해야 한다.

### 2. 한국 PII 엔티티 커버리지 점검·보강 [S]

- **문제**: 경쟁이 KR 식별자 유형 목록을 공개해 **영업 자리에서 체크리스트 비교가 시작됐는데**(Theori 8종), 우리는 "무엇을 잡는가"를 문서 한 장으로 답하지 못한다. 인벤토리는 regex 5종(주민번호·KR전화·KR계좌·카드·IP)이라 적고 있지만 저장소의 패턴 인식기는 10 라벨이다(아래 SGT 현재) — **우리 문서가 우리 제품보다 적게 적혀 있다.**
- **무엇**: KR 식별자 유형 커버리지를 먼저 **점검**하고(GLiNER 12 라벨 + regex 5 라벨이 실제로 무엇을 잡는지), 누락된 유형(사업자등록번호·건강보험번호 등)을 검증규칙 포함 regex로 보강. 점검 결과가 "이미 커버"면 그대로 종료하는 것이 정상 결과다.
  - **풀구성**: 점검 산출물은 유형×존재×평가셋 포함 여부 표(문서). 라벨을 실제로 추가·변경하면 노출 경로는 admin 탐지 설정 화면의 PII threshold 목록 + `init_script.sql` 시드(`sgt_app_config`) 갱신.
  - **최소구성**: 별도 화면 작업 없음 — sgtctl은 threshold 키를 **파일에서 읽어오지 하드코딩하지 않으므로**(sgt-ctl README) 라벨이 늘면 자동으로 목록에 뜬다. `pii_entity_thresholds.json` 기본값만 맞으면 된다.
- **동작 시나리오**: 입력 "사업자등록번호 123-45-67890 법인 계좌 개설 절차 알려줘" → **현재**: `KR_BUSINESS_REG` 패턴 인식기가 존재하고 문맥 게이트 대상(`CONTEXT_GATED_ENTITIES`)이라 검출·마스킹된다 → 이 후보의 점검 산출물은 "사업자등록번호 = 있음, 평가셋 포함" 한 줄이 되고 **추가 개발 없이 종료**한다. 반대로 `KR_MEDICAL_INSURANCE`는 인식기는 있으나 코드 주석상 **검증 측정(13라벨) 밖**이라 "있지만 재본 적 없음"으로 분류돼, 보강이 아니라 **평가셋 편입**이 작업이 된다.
- **왜 지금**: 경쟁이 공개한 한국어 PII 대상 유형 목록이 처음 확보됐다 — 주민등록번호·**사업자등록번호·건강보험번호**·전화번호·이메일·계좌번호·주소·이름(D§Q5, [https://theori.io/ko/blog/korean-pii-detection-benchmark](https://theori.io/ko/blog/korean-pii-detection-benchmark) ). 글로벌 제품은 KR 내장 엔티티가 0이라 이 칸은 국내 3사와의 싸움이고(G§Q4, [https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-supported-languages.html](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-supported-languages.html) ), 유형 목록은 영업 현장에서 체크리스트로 그대로 쓰인다.
- **경쟁 현황**: Theori αprism이 KR 유형 8종을 명시(측정 수치는 자사 벤치마크라 비교 근거로 쓰지 않음). 글로벌 6곳은 전부 커스텀 regex 위임.
- **SGT 현재**: regex 5종(주민번호·KR전화·KR계좌·카드·IP) + GLiNER 12 라벨 — **사업자등록번호·건강보험번호 포함 여부가 인벤토리에 명시돼 있지 않다**(inventory: PII 행).
  - **저장소 실측**: 패턴 인식기(`recognizer_pattern.py`)의 `supported_entity`는 **10종** — `KR_ID`·`KR_PHONE`·`KR_BANK_ACCOUNT`·`CREDIT_CARD`·`EMAIL_ADDRESS`·`KR_PASSPORT`·`KR_DRIVER_LICENSE`·`KR_BUSINESS_REG`·`KR_CORP_REG`·`KR_MEDICAL_INSURANCE`. 즉 **경쟁이 내세운 8종 중 사업자등록번호·건강보험번호는 이미 구현돼 있다.**
  - 임계값 카논(`entity_threshold_config.py`)에도 같은 라벨 + `KR_ADDRESS_UNIT`이 있고, GLiNER 인식기도 세 라벨의 문맥 키워드를 갖는다. 사업자/법인 등록번호는 문맥 억제 게이트 대상이나 `KR_MEDICAL_INSURANCE`**는 게이트 제외**(코드 주석: 보호 지시어 계열 부재 + 검증 측정 13라벨 밖 + FPR 하네스 실측 FP 0건).
  - **따라서 이 후보의 실제 잔여 작업은 "신규 라벨 추가"가 아니라 ① 인벤토리·영업 자료를 저장소 실측에 맞추기 ② 평가셋 밖 라벨의 측정 편입**일 가능성이 높다. 체크섬 검증 규칙의 실제 구현 범위는 `미확인`(`pii_validators.py`에 `KR_CORP_REG` 관련 서술은 확인).
- **완료 판정**: (1) KR 식별자 유형 × (인식기 유무 / 평가셋 포함 / 체크섬 검증 유무) 표가 문서로 존재하고 **인벤토리와 일치**한다. (2) Theori 공개 8종 각각에 대해 "있음/없음/평가 밖" 판정이 붙는다. (3) 라벨을 추가했다면 로컬 폴백 JSON과 admin 시드 값이 **같다**(#720과 같은 불일치를 새로 만들지 않는다). (4) 추가·편입 후 법령 clean 코퍼스 FPR이 합의 상한을 넘지 않는다.
- **규모 근거 [S]**: 점검만이면 문서 작업 1주 이내. **라벨을 실제로 추가하면 [S]가 아니다** — admin↔owasp 설정 왕복(#838)·시드 정합(#720)·`init_script.sql` 변경 시 **수동 DB 마이그레이션 1세트**·FP 재측정이 붙는다(3-critique R5의 지적과 동일). 즉 이 표기는 "점검까지가 [S], 보강은 별건"이라는 전제에서만 성립한다.
- **리스크**: 검증숫자(체크섬) 규칙이 없는 유형은 오탐이 늘어 후보 1과 세트로만 안전하다. 라벨 추가는 admin↔owasp 설정 왕복(#838)과 임계값 시드 정합(#720)을 함께 건드린다.
- **중복 가능 이슈**: #875, #833(영어 인식기 미동작).
- **기존 이슈 판정**:
  - **#875 → 분리**. #875는 이미 존재하는 라벨(`LOCATION`·`ORGANIZATION`)의 **recall 개선**(행정동 gazetteer 편입·브랜드 유한목록)이고, 이 후보는 **식별자 유형 커버리지 점검**이다. 겹치는 것은 재측정 게이트뿐.
  - **#833 → 분리**. 영어 경로(`PresidioPiiRecognizer`)가 `supported_entities` 반환 타입 결함으로 항상 0건인 **버그**이며 원인·수정 방향이 이미 특정돼 있다. 이 후보의 점검이 그 사실을 다시 확인할 수는 있으나 후보가 이 버그를 흡수하면 티켓 하나가 기획 승인을 기다리게 된다 — 별도로 먼저 닫는 것이 맞다.



### 3. 탐지 민감도 프리셋 (관대/기본/엄격) [M]

- **문제**: 민감도 축이 **세 서비스가 서로 다른 형상**으로 흩어져 있다 — PII는 `pii_entity_thresholds.json`, toxic은 `toxic_config.json`, JB만 **모델 설정 파일 안**(#826 본문 표). 그래서 오탐이 터졌을 때 JB 민감도 하나를 낮추려면 `model_path`를 포함한 모델 설정 전체를 오버레이해야 하고, 그 순간 그 사이트의 모델 경로가 고정돼 **이후 모델 업그레이드가 조용히 덮인다**(#826). 현장이 라벨별로 조정하는 대신 `_default`를 1.1로 올려 통째로 끈 것도(#816 §1) 이 구조와 무관하지 않다.
- **무엇**: 흩어진 민감도 축(toxic 카테고리별 threshold, PII per-entity threshold, JB 민감도)을 **하나의 프리셋 3~4단계**로 묶어 운영자가 한 손잡이로 조정. 개별 threshold는 고급 설정으로 유지하되 우선순위 규칙을 명문화.
  - **풀구성(admin UI)**: `detection/config.html`에 프리셋 선택을 추가한다. 현재 이 화면에는 PII 엔티티별 슬라이더와 toxic 카테고리별 슬라이더 + "설정값 되돌리기"만 있고 **JB 관련 항목은 없다**(저장소 검색 0건) → JB를 프리셋에 넣으려면 #826이 선행이다.
  - **최소구성(sgtctl)**: 현재는 `toxic_config.json`·`pii_entity_thresholds.json`을 **키 단위**로 편집하는 화면이다. 여기에 프리셋 항목을 추가해 한 번의 편집이 두 파일을 함께 쓰도록 한다(금칙어가 `words`+`enabled` 두 키를 함께 쓰는 기존 패턴과 동일). 반영은 롤링 재기동.
  - 프리셋 이름·값은 **풀·최소가 같은 정의**를 써야 한다(값이 갈리면 #720의 재현).
- **동작 시나리오**: 증권 법령 질의("테러자금 의심거래 보고 기준 알려줘" 류 — #781이 최고 위험군으로 분류한 카테고리)에서 오탐이 급증 → 운영자가 프리셋을 **관대**로 내린다 → PII·toxic·JB 세 축의 값이 **미리 정의된 조합**으로 한 번에 이동하고, 화면은 "이 프리셋에서 사실상 꺼지는 라벨" 목록을 함께 보여준다. 현재는 같은 상황에서 운영자가 각 파일을 따로 열어 `1.1` 같은 범위 밖 sentinel을 손으로 적어야 하고(sgtctl은 클램프하지 않는다고 README에 명시), 무엇이 꺼졌는지는 아무 화면에도 뜨지 않는다.
- **왜 지금**: Lakera가 정책별 L1(Lenient, "very few false positives")~L4(Paranoid)로 **민감도를 제품 기능으로 승격**했고, 이것이 확인된 오탐 대응 수단 중 가장 구체적이다(G§Q5-c, [https://docs.lakera.ai/docs/policies](https://docs.lakera.ai/docs/policies) ). 폐쇄망 고객사엔 ML 담당자가 없어 축별 수치 조정은 실질적으로 미사용 기능이 된다.
- **경쟁 현황**: 명시적 민감도 등급은 Lakera 1곳(L1~L4). Bedrock의 카테고리별 강도는 원문 미확인, 나머지 4곳 미확인.
- **SGT 현재**: 축은 이미 다 있으나 **일관성이 없다** — threshold는 기본 mDeBERTa만 지원(대안 Kanana 미지원), JB 민감도는 모델 설정에 묶여 있고(#826), PII per-entity 임계값은 로컬 폴백↔admin 시드가 불일치(#720)(inventory: 유의 사항).
  - **저장소 실측**: 프리셋 유사물이 하나 있다 — `compliance_modes.json`(kr_pipa / us_hipaa / eu_gdpr / strict)과 `unified_policy.json`. 다만 이들은 **주소 마스킹 정책**(보존 레벨·마스킹 문자) 전용이지 탐지 민감도 프리셋이 아니다. 네이밍·화면 배치에서 이 둘과 충돌하지 않게 하는 것이 설계 제약이다.
  - **저장소 실측**: sgtctl은 threshold 키를 하드코딩하지 않고 현재 파일에서 읽으며, 한 항목만 바꿔도 **파일 전체가 교체**된다(부분 병합 아님) — 프리셋을 파일 단위로 갈아끼우는 방식과 잘 맞는다.
- **완료 판정**: (1) 프리셋 하나를 고르면 PII·toxic(·#826 이후 JB) 값이 **한 번의 조작으로** 함께 바뀐다. (2) 프리셋과 개별 threshold가 동시에 지정됐을 때 **어느 쪽이 이기는지**가 문서와 코드에서 같고, 화면·CLI가 그 결과값을 보여준다. (3) 각 프리셋에서 **사실상 비활성이 되는 라벨 목록**이 적용 전에 표시된다. (4) 같은 프리셋 이름으로 풀·최소 두 구성에서 동일한 탐지 결과가 나온다.
- **규모 근거 [M]**: 코드(admin 화면 + sgtctl 화면 + 우선순위 해석 1곳) + 설정 전파 양쪽 + 문서(README 3곳). **DB 마이그레이션 조건부 포함** — 프리셋 기본값을 `init_script.sql` 시드로 넣으면 수동 마이그레이션 1세트가 붙는다. 재측정은 프리셋 단계마다 1회씩 필요(단계 수 × FPR/recall). **#826·#720을 선행으로 포함하면 [M] 상단이거나 [L]** — 원안 표기는 그 둘을 별건으로 둔 전제다.
- **리스크**: 프리셋과 개별 threshold의 **이중 원장** — 어느 쪽이 이기는지 정하지 않으면 #720류 불일치를 하나 더 만든다. 실질 작업의 절반은 신기능이 아니라 기존 축 정리다.
- **중복 가능 이슈**: #826, #720, #816.
- **기존 이슈 판정**:
  - **#826 → 분리(선행 의존)**. JB 민감도를 모델 설정에서 떼어내는 리팩터는 이 후보 없이도 독립 가치가 있고(모델 경로 오버레이가 업그레이드를 덮는 결함), 이 후보가 JB 축을 포함하려면 **먼저 닫혀야** 한다.
  - **#720 → 분리(선행 의존)**. 로컬 폴백↔admin 시드 불일치는 후보 승인 여부와 무관하게 존재하는 결함이며, 정합이 안 된 상태에서 프리셋을 얹으면 **원장이 셋**이 된다.
  - **#816 → 분리**. #816의 산출물은 리포트(A/B 측정)이고 이 후보는 제품 기능이다. 관계는 중복이 아니라 **입력** — 프리셋 각 단계의 값을 정할 근거표가 #816 §1이다.



### 4. 정책 영향 미리보기 (감사 로그 재판정) [L]

- **문제**: 설정을 바꾼 결과를 **적용 전에는 아무도 볼 수 없다.** 지금 그 계산은 사람이 사후에 하고 있다 — #816(개발 기본값 vs 현장 운영값 A/B 리포트)과 #873(베타오픈 주간 로그 3주 캠페인)이 정확히 "저장된 로그를 다른 설정으로 다시 돌려보는" 작업이며, 설치형이라 잘못 조정하면 되돌리는 데 고객 유지보수 창이 필요하다.
- **무엇**: 저장된 탐지 감사 로그를 새 설정(프리셋/예외 사전)으로 **재판정**해 "차단 건수가 몇 % 변하는지"를 적용 전에 보여주는 기능. 운영 트래픽에 적용하지 않고 미리 본다.
  - **풀구성 전용**이다. admin 탐지 설정 화면에서 "이 설정으로 지난 N일 재판정" 버튼 → 결과 표(현재 설정 vs 후보 설정의 탐지 건수·라벨별 증감).
  - **최소구성은 불가** — admin·DB가 없어 재판정할 로그 저장소 자체가 없다. 최소구성 고객에게 남는 경로는 sgtctl로 값을 바꾸고 **롤링 재기동 후 관찰**하는 현행 방식이며, 이 후보는 그 격차를 좁히지 않는다.
- **동작 시나리오**: 운영자가 `ORGANIZATION`을 1.1(현장값) → 0.6(개발 기본값)으로 바꾸려 한다 → 적용 전에 "지난 7일 감사 로그 N건 재판정"을 누른다 → 결과: 차단 +X건(그중 조직명 Y건, 법인명이 대부분), 라벨별 증감 표. 운영자는 그 증가폭이 앞단 agent 흐름을 끊을 수준인지 보고 결정한다. 이 판단을 지금은 우리가 대신 계산해 리포트로 제출하고 있다(#816·#873).
- **왜 지금**: Lakera의 Policy Impact Simulator가 "과거 트래픽으로 민감도별 flagging rate를 비교"하는 기능을 이미 제품화했다(G§Q5-c, [https://docs.lakera.ai/docs/defenses](https://docs.lakera.ai/docs/defenses) ). 설치형·폐쇄망은 **우리가 고객 트래픽을 볼 수 없고 롤백에 유지보수 창이 필요**하므로, 시행착오 조정 자체가 고객 리스크다 — 미리보기의 가치가 SaaS보다 크다.
- **경쟁 현황**: 확인된 6곳 중 시뮬레이터를 문서화한 곳은 Lakera 1곳.
- **SGT 현재**: 탐지 요청 감사 DB와 채팅 세션 감사는 있으나 재판정 기능 없음. **최소구성엔 감사 DB 자체가 없다**(inventory: 최소구성 한계) → 풀구성 전용 기능이 된다.
  - **저장소 실측(재판정 입력의 존재 여부)**: 원문은 남는다 — `sgt_chat_history`에 `query`/`original_query`/`answer`/`original_answer`, `sgt_owasp_api_event`에 `request_content`/`response_content`(TEXT). 탐지 결과는 `sgt_chat_detection`(JSONB, `query_id` 유니크)와 같은 이벤트 행의 `pii_items`/`predictions`/`jailbreak_detect`/`banword_detect`에 남는다.
  - **없는 것**: 정답 라벨. 어느 테이블에도 없다 → 재판정이 산출할 수 있는 값은 **탐지 건수·분포의 변화**까지이고 F1은 정의되지 않는다(#873 제약 1과 동일).
  - **없는 것**: 재판정 실행 경로(배치·큐·자원 격리) 일체. 현재 재판정은 GPU 박스에서 툴킷(#802)으로 수동 수행한다.
- **완료 판정**: (1) 설정 변경 **적용 없이** 결과 표가 나온다(운영 설정은 그대로다). (2) 재판정 실행이 운영 추론과 자원을 다투지 않는다(별도 큐/제한 — 판정 기준을 정한다). (3) 결과 표에 **"이 수치는 정답 라벨 없는 건수 비교"**라는 한계가 함께 표기된다. (4) 재판정 대상 로그의 보존 기간·원문 보관 정책이 화면에 드러나고, 기간이 없으면 기능이 성립하지 않음을 명시한다.
- **규모 근거 [L]**: 신규 화면 + 재판정 실행 경로(비동기 잡·진행률) + 결과 저장 스키마 → **DB 마이그레이션 1세트 포함 가능성이 높다**. GPU 재추론 자원 계획과 로그 보존 정책 결정이 코드 밖 작업으로 붙는다. 최소구성 몫은 0(풀구성 전용)이라 그만큼은 빠진다.
- **리스크**: 재판정은 GPU 재추론 비용을 부르고(운영 트래픽과 자원 경합), 감사 로그에 원문이 남아 있어야 성립한다 — 원문 보존은 그 자체로 민감정보 축적 문제다. 후보 1·3이 먼저 있어야 의미가 있으므로 **동시 착수 금지**.
  - **추가 확인(#873 본문이 이미 명시한 제약)**: ① 로그에 정답 라벨이 없어 F1 측정 불가 — "탐지 건수 변화만으론 보수적 독자에겐 약하다", ② selection bias — 로그는 현장 config로 걸러진 **통과분**이라 차단돼 안 남은 트래픽은 볼 수 없다, ③ 로그 본문이 원문인지 마스킹본인지 미확인(마스킹본이면 PII 측정이 과소평가). 이 세 제약은 기능화해도 사라지지 않는다.
- **중복 가능 이슈**: #873, #816(현재 사람이 수동 리포트로 하고 있는 일).
- **기존 이슈 판정**:
  - **#873 → 흡수**(이 후보를 #873 트랙으로 접는다). #873은 같은 재판정을 3주 캠페인으로 **이미 수행 중**이고 호출·집계 하네스도 #802로 존재한다. 제품 기능화는 그 캠페인이 "재판정 수치가 고객 설득에 실제로 통한다"를 보인 **뒤에** 별건으로 여는 것이 순서다.
  - **#816 → 분리**. 1회성 A/B 리포트(2026-08 납품 대응)로 성격이 다르다. 이 후보와의 관계는 중복이 아니라 근거 제공이다.



### 5. 폐쇄망 번들 완결성 — 모델 수급 구멍 제거 + 설치 전 자가검증 [M]

- **문제**: 가이드대로 폐쇄망 번들을 만들면 **toxic 모델을 손에 넣을 방법이 없다.** #762가 실측으로 지목했고, 오늘 재확인해도 그대로다 — 번들 생성기(`sgt-owasp/scripts/package_models_inference.py`)는 `onnx/`*를 "불필요 포맷"으로 제외하고(L105) `triton_repo` 문자열은 **0건**인데, 오프라인 가이드는 `triton_repo/toxic_classifier`가 **이미 있다고 전제**하고 복사만 시킨다. toxic의 `model_type` 기본값이 `safe_classification`(Triton ONNX 경로)이라 **아무 결정을 안 하면 이 경로로 간다.**
- **무엇**: 오프라인 번들에서 수동 조달로 남은 모델 경로를 없애고(특히 toxic ONNX·NAS 수동 조달분), 반입 후 **설치 전에 번들 자체가 완결됐는지 검사**하는 단계를 표준 절차에 넣는다.
  - **구성 무관**(풀·최소 동일) — 산출물은 번들 생성기와 반입 후 검사 스크립트다. 운영자 조작 경로는 admin UI도 sgtctl도 아니고 **설치 절차의 셸 단계**다.
  - 검사 단계는 기존 `helm/check-models.sh`(설치 전 모델 존재 확인)와 `MODEL_VERSIONS.json`(sha256 원장)을 잇는 형태로 붙인다 — 신규 도구를 만들 자리가 아니다.
- **동작 시나리오**: 한국증권금융 toxic 첫 배포 — 가이드대로 번들을 만들어 반입 → `triton_repo/toxic_classifier/1/model.onnx`(1.74GB)가 없다 → Triton이 toxic을 0개 로드 → owasp `/health/readiness`가 503으로 잡아낸다(#760 이후 fail-loud) → **현장에서 배포가 뜨지 않는다.** 후보 적용 후: 번들 생성 시 toxic을 선택하면 ONNX가 포함되고 `MODEL_VERSIONS.json`이 sha256으로 추적하며, 반입 직후 검사 스크립트가 누락·해시 불일치를 **설치 전에** 잡는다.
- **왜 지금**: 경쟁 전원이 에어갭을 **문구로만** 주장하고 근거 문서가 없다 — Lakera조차 오프라인 라이선스 활성화·모델 패키징 미확인(G§Q1, [https://docs.lakera.ai/docs/selfhosting](https://docs.lakera.ai/docs/selfhosting) ), F5는 제품 페이지 문구([https://www.f5.com/products/ai-guardrails](https://www.f5.com/products/ai-guardrails) ), 국내는 근거 제시 0곳(D§Q2). **"증명 가능한 에어갭"이 유일하게 비어 있는 경쟁 칸**이고, 우리 번들에 수동 단계가 남아 있으면 그 주장을 우리도 못 한다.
  - ⚠️ 이 "왜 지금"은 [3-critique.md](3-critique.md) R2에서 정면 반박됐다(공개 문서 `platform.lakera.ai/docs/self-hosted-setup` 존재 → 조사가 접근 실패를 부재로 바꿨다는 지적). **시장 근거가 무너져도 #762의 배포 결함 자체는 남는다** — 그 경우 이 항목은 후보가 아니라 버그 수정으로 처리된다.
- **경쟁 현황**: 매트릭스 배포 모델 열에서 에어갭이 `[공식]` 근거로 확인된 행 0개(Bedrock은 명시적 불가).
- **SGT 현재**: 2단계 오프라인 패키지 절차와 check-models.sh는 있으나, Kanana 8B 등 일부 모델이 HF 미배포로 **NAS 수동 조달**이고(inventory: 유의 사항) toxic ONNX 획득 경로가 번들에 없다(#762).
  - **저장소 실측**: `docs/offline-package-guide.md`·`helm/check-models.sh` 존재 확인. 패키저의 `onnx/`* 제외(L105)와 `triton_repo` 0건도 오늘 재확인 — #762는 **미해결**이다.
  - #762 본문에 따르면 HF 저장소에 `onnx/model.onnx`가 이미 있어 **변환이 아니라 "제외를 푸는" 문제**이며, 번들 매니페스트가 `rglob("*")`이라 넣기만 하면 sha256 추적이 자동으로 따라온다.
- **완료 판정**(#762 수용 기준을 그대로 씨앗으로 쓴다): (1) toxic 포함 폐쇄망 번들 생성 시 `triton_repo/toxic_classifier`가 번들에 포함된다. (2) `MODEL_VERSIONS.json`이 그 파일을 sha256으로 추적한다. (3) toxic 미포함 번들(현대차증권 등)은 크기가 늘지 않는다. (4) `docs/offline-package-guide.md`의 복사 절차가 실제 번들 산출물과 일치하고, 반입 후 검사 단계가 절차에 포함된다.
- **규모 근거 [M]**: 코드(패키저 + 검사 스크립트) + 문서(오프라인 가이드·helm README) + 릴리스 재빌드/재검증 1회. **DB 마이그레이션 없음**, 설정 전파 없음(설치 시점 산출물). 다만 모델 재배포 전 **라이선스 확인**이 코드 밖 선행 작업으로 붙는다.
- **리스크**: 사실상 #762의 확장이라 **중복 발주 위험이 가장 큰 후보**다. 모델 재배포는 라이선스 확인이 선행돼야 하고(Gemma Terms 등 외부 모델 조항), 개발 후보가 아니라 릴리스 엔지니어링 작업이라 2인 중 누구 몫인지 불분명하다.
- **중복 가능 이슈**: #762(거의 동일), #519, #801.
- **기존 이슈 판정**:
  - **#762 → 흡수**(이 후보를 #762로 접는다). 실측 근거·제안 3안·수용 기준이 이미 다 적혀 있고 담당자도 지정돼 있다. 기획 후보로 다시 세우면 같은 일을 두 번 발주하는 것이다.
  - **#519 → 분리**. 현대차증권 패키징은 docker compose 기반 납품 건이고 **PII+JB만 쓰므로 toxic ONNX 경로에 걸리지 않는다**. 다만 2인 중 1명의 일정을 이미 점유하고 있다는 사실은 착수 시기 판단에 들어가야 한다.

### 6. 공개 벤치마크 기반 측정 기준 정립 [M]

- **문제**: 우리 수치가 여러 문서에 흩어져 있고 **서로 다른 자로 잰 값**이라, 고객 PM이 나란히 놓고 물으면 답이 길어진다. 이 문제는 이미 티켓에 올라와 있다 — #873의 AC에 "**문서 정합성 대응표**: 슬랙 첨부(v5-rc33 gold F1) / #729(법령 112종 clean-corpus FPR — gold 라벨이 없어 F1이 정의되지 않는 측정) / #816 리포트(gold 11,702문장 A/B)는 서로 다른 셋·다른 지표"를 1장 표로 정리해 전달하라고 적혀 있다.
- **무엇**: 경쟁 수치를 반박하는 게 아니라 **우리 수치의 측정 기준을 문서로 고정**한다 — 데이터셋 구성·strict 판정 정의·재현 절차를 공개 가능한 형태로 정리하고, 가능한 범위에서 공개 벤치마크를 1개 이상 편입.
  - **제품 형상이 아니다**(admin UI·sgtctl 경로 없음). 산출물은 문서 + 평가 하네스 설정이며 풀·최소 구성과 무관하다.
  - 굳이 화면에 노출한다면 경로는 #93(모델과 성능지표 파일을 함께 전달해 화면에 표시)이며, **그것은 이 후보의 범위 밖**이다.
- **동작 시나리오**: 영업 자리에서 "Theori는 89.0인데 SGT는 0.8531이면 낮은 것 아니냐"는 질문을 받는다 → 지금은 답이 사람마다 달라진다 → 후보 적용 후에는 1장짜리 대응표를 편다: 각 수치가 **어느 데이터셋·어느 라벨 체계·어떤 strict 정의·언제** 측정됐는지, 그리고 두 값이 동일 선상 비교가 아닌 이유. 여기에 공개 벤치마크 1개(예: JB 축의 FENCE·KFinEval-Pilot — #874가 이미 편입 판정을 마친 후보들) 수치가 붙으면 제3자 자를 하나 공유하게 된다.
- **왜 지금**: 경쟁 3사가 각자 수치를 내놓았고(Theori 89.0·이로운 97.88%·파수 93.1%) **전부 데이터셋·과제·기준이 달라 비교가 성립하지 않는다**(D§Q5 경고, [https://theori.io/ko/blog/korean-pii-detection-benchmark](https://theori.io/ko/blog/korean-pii-detection-benchmark) ). 수치 경쟁에 뛰어드는 대신 "우리 수치가 무엇을 쟀는지"를 먼저 고정해야 영업 자리에서 방어가 된다.
- **경쟁 현황**: 3사 모두 자사 벤치마크·자사 발표. 제3자 공통 벤치마크는 확인되지 않음.
- **SGT 현재**: strict micro F1 0.8531(PII)·탈옥 97.5%는 있으나 **레이턴시 등 공식 수치는 미측정이며 "미측정"이 정직한 값**(inventory: 유의 사항).
  - **이슈 실측(2026-08-12 확인)**: #874가 이 일의 상당 부분을 **이미 했다** — AC 5건 중 3건이 `[x]`다(공개 벤치 조사·판정 FENCE/KFinEval/mosscap/FinSafetyBench 라이선스·구성·규모 → 편입/제외 판정 / 골든셋 v1.1 구축 / PII 골든셋 경로 확보). 남은 2건은 HF backport와 금융 파트 고객 승인.
  - #874의 사전 판단도 이미 기록돼 있다: **PII는 공개 벤치마크로 해결되지 않고**(한국어 금융 PII 골든셋이 공개 시장에 사실상 부재), **JB는 공개 벤치마크가 유효**하다. 즉 "공개 벤치 1개 이상 편입"은 축에 따라 성립 여부가 갈린다.
- **완료 판정**: (1) 우리가 대외에 쓰는 수치 각각에 **데이터셋·라벨 체계·판정 정의·측정일·재현 명령**이 붙은 표가 하나 존재한다. (2) 서로 다른 문서(슬랙·#729·#816)의 수치 차이가 그 표 하나로 설명된다. (3) JB 축에 공개 벤치마크 1개가 편입되고 **폐쇄망 반입·상용 평가 사용 가능 여부(라이선스)**가 판정돼 기록된다. (4) 표에 없는 수치는 대외 자료에 쓰지 않는다는 규칙이 문서화된다.
- **규모 근거 [M]**: 문서 + 평가 하네스 설정·재현 스크립트 + 재측정 1회. **코드 변경·마이그레이션 없음.** 다만 공개 벤치 편입은 데이터셋 반입(오프라인 패키징)과 라이선스 검토가 붙고, #874의 잔여 AC(HF backport·고객 승인)와 일정이 얽힌다.
- **리스크**: 비교 마케팅 유혹 — 기준 병기 없이 숫자만 나가면 이번 조사의 경고를 우리가 어기는 셈이다. 골든셋 구축은 이미 진행 중인 이슈와 정면으로 겹친다.
- **중복 가능 이슈**: #874(골든셋 + 공개 벤치마크 편입 검토), #93(모델 성능 지표), #765.
- **기존 이슈 판정**:
  - **#874 → 흡수**(이 후보를 #874로 접는다). 공개 벤치 판정·골든셋 v1.1이 이미 완료 상태이므로 신규 후보로 세우면 완료된 일을 다시 발주한다. 이 후보에서 **#874에 없는 몫은 "대외용 측정 기준 대응표"뿐**이며, 그것도 #873 AC에 이미 항목으로 존재한다 → 남는 것은 그 산출물을 **사내 문서에서 대외 공개 가능한 형태로 승격**하는 작업이다.
  - **#93 → 분리**. 성능 지표를 관리 화면에 표시하는 제품 기능이고, 이 후보는 그 지표의 **정의**를 만드는 일이다. 순서상 이 후보가 먼저다.
  - **#765 → 분리**. 공격 변종 recall 회귀 게이트(agent_secure 하네스 최소 이식)로, 측정 **기준 문서화**가 아니라 상시 **회귀 감시** 축이다. 다만 "우리 수치가 무엇을 쟀는가"의 답에 이 게이트 결과가 들어가게 되므로 산출물을 공유한다.
